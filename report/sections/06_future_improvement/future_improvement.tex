\section{Future Improvement}

It would be interesting to try extending this experiment across a wider range of
heap implementations, especially focusing on making small modifications to each
of the currently selected heaps. We could observe if different optimisations
actually produce a real-world impact under the fairly complex runtime
conditions of a min-heap. This would be particularly interesting for the
Brodal-Okasaki heap, and to also add the imperative Brodal min-heap~\cite{brodal1996worst} as another point
of comparison.

The present interface identifies a queue entry by its vertex number; this
requires additional work to support \code{heap_decrease_key}, and the current
index tables do not support multiple entries for a vertex alongside
\code{heap_decrease_key}. Instead, each push could be assigned a unique
identifier, used for looking up the node in \code{heap_decrease_key}, which would
be a more correct implementation and remove the need for the positive and
negative cancellation lists in Brodal-Okasaki that slow the implementation down.
Since the edge case that would cause an incorrect \code{heap_decrease_key}
does not arise under Dijkstra's algorithm, we decided to skip this feature.

Our hardware counters show that every working set stayed on chip: last-level
cache misses never exceeded $1.2$ per vertex. Running graphs whose working set
is several times the 12~MiB last-level cache would test whether the binary
heap's lead holds, or grows, once heap accesses have to go to main memory.

Finally, a direct test of Hypothesis~1.2 needs inputs that actually exercise
decrease-key. Uniform random weights cause at most about two decrease-key calls
per vertex (Section~5). Constructions in which most vertices are first reached
through heavy edges and then improved repeatedly by lighter paths can make
almost every relaxation succeed, giving the pairing and Fibonacci heaps the
workload their theoretical bounds are designed for.

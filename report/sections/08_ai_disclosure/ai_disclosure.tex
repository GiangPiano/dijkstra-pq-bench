\section{AI Disclosure}

\subsection{Oscar's Experience}

% Makefile troubles
% Useful for perf / mem tests and graphics

This was my first time using AI in any meaningful manner. There was both good
and bad.

When I knew exactly the changes that I wanted LLM's were very helpful to quickly
make changes that would have otherwise been tedious. Certain tasks were not
particularly appealing to work on, but using LLM generated code and auditing it
meant that I could quickly get to a place where I was happy. Notable parts of
the project that were AI generated are the perf and mem tests, some of the graph
generation logic, the plot generation, and the presentation.

On the other hand, when not enough specific guidance was given, or if another
group member who had a less clear image of the outputs they wanted had prompted
the LLM, I'd often find that the produced code was overly brittle. For instance,
the early implementations of perf recorded intel specific events, and were not
portable at all. The early perf and mem tests also hardcoded the graph and heap
names, and would not have held up well to changes in the inputs.

However, despite these downfalls, it was easy to later correct the LLM, modifying
the scripts to not hard code the systems by pointing them to good examples and
motivations for why tasks should be completed in the way I wanted them to be
done.

One aspect I did not like LLMs touching was the Makefile. They were all too
happy to forever tack on additional targets and variables without considering
how to integrate with the existing structures. Often a group member would ask
the LLM to quick and dirty add their outputs to the Makefile, and then I would
review and restructure the project's build process as the requirements and
structure changed. The LLM Makefile contributions were always terribly
implemented and completely replaced when I would manually audit the file.

Outside of generation, I found that using an LLM was very helpful for analysing
how to optimise the Brodal-Okasaki heap. Claude identified that meld is not
used, so bootstrapping is no longer necessary, and gave me the idea to put all
cells in a buffer by suggesting that I run my own free list for the allocations,
which is not quite the same thing. After I had rewritten the min heap, Claude
was able to quickly catch a number of small mistakes I had made in the rewrite,
before I wasted time running and debugging it. I quite enjoyed this explorative
and feedback usage, where the LLM did not generate code for me, but was instead
used to get a different perspective, or to simplify the reasoning about a very
complex implementation.

For my first experience interacting with LLM's on a larger scale in a project, I
was quite impressed with how much time it saved the group, but felt I always
needed to spend time properly posing questions to the LLM and reviewing the
outputs, as there would always be something wrong with the first attempt. I
suspect recent improvements in the quality of tools means I'll need to begin
taking them more seriously, and come to terms that they will be part of software
development going forward.

\subsection{Truong Giang's Experience}

I used Claude Code to scaffold the project structure, since my task is the very first step in the project. Initially, Claude implemented a vector to use as adjacency list for the graph representation. Since our project focuses on benchmarking the heap implementation, I wanted to minimise the impact of other operations outside of the heap. So I ask Claude to change that to a more effective format, so it suggested using CSR table. I then announce my group about this change before approving it.

One thing I found AI to be particularly helpful is when debugging pointers usage and memory allocation. Since C offers raw control over the allocated memory space, it is very easy to miss calculate the required size for the allocation, eventually leading to a silent crash. I encountered a bug in the binary heap's \code{heap_pop} function, but the assert failed in the \code{decrease_key} function instead. Claude Code instantly caught this, saving me a lot of time trying to debug it manually.

I noticed that AI tends to overly engineer the solution when the given input is not specific enough. An example is when we decided to implement another variant of the Dijkstra's algorithm. Since we have a single interface to call the Dijkstra's algorithm, it initially duplicated to another file, then rely on Makefile to dynamically link different objects to the selected algorithm. We then simplified it to have just a single file containing both variants.

It also hallucinates and overcomplicate the approach on more complex tasks. We used Claude to generate the presentation slides based on our report, the codebase, and the video requirement. This task requires the AI to review everything we have in our repository. Initially, it included some random benchmark figures that does not even exist in our codebase, and it tries to fit too much detail in a 15 minutes video. I then learnt that using AI effectively is not just about giving it as much information as possible, but also to limit on the scope of the problem.

When generating the benchmark visualisations, AI overlooked the fact that the benchmarking library already supported exporting results directly to \code{.csv} files. Instead, it created a separate Python parser to read the output and convert it into a pandas DataFrame. This added unnecessary complexity to the workflow. We eventually discarded that implementation and provided AI with more context about the library's existing CSV export functionality so it could use it instead.

\subsection{Tung's Experience}
First, I started by digesting this assignment description with Gemini Flash 3.8, I asked it to point out the main pain points to look out while doing this project. Once that is done, I relay my understand with the team. After that, I chose to implement Pairing and Fibonacci heaps. I then ask Gemini to briefly introduce me to these heaps and provide good source on YouTube. I then check my understand with Gemini again by draft up the pseudocode and asking it to correct any mistake. Since these heaps were quite popular, the discussion session with the AI was fruitful as I can cross check myself with the AI and other sources, in which it also provided. So far, the AI has done a good job of helping me to catch up with the knowledge of this project.

Second, I move on to implement the code for these heaps, and move on to using Antigravity with Gemini 3.8 Flash. I wrote to code on my own and then ask the AI to fix it. The AI was very efficient with writing code, it did struggle with syncing my code to the rest of the codebase. Basically, instead of defining two parameters, we group it into an \code{Item}. But, my AI just code out the two parameters individually, a minor mistake and was easily self-checked and fixed. Later on, the we need to add a \code{heap_decrease_key} codebase wide. This was a repetitive task, in which the AI was very good at. 

Third, I then plan ahead for the benchmark, i.e. what kind of experiment we should do. The AI was good here since it suggest hardware test, in which I'm not that familiar with. However, it went over the boat and just list a lot of things. After a team meeting, we only pick some of what it suggested, with the constraint of keeping thing not being too convoluted. I then had a back and forth session with Gemini on Antigravity on design the pipeline for each experiment, which went smoothly. I then ask the AI to implement these pipeline in the codebase. Here, the AI also kept looking for shortcut and was cutting down on test input. I had to explicitly tell it to \emph{not} be lazy, still it did not follow through. It was not until the other day, when me and Oscar were getting together to do some code review, where Oscar was checking the Makefile and looking through the output manually. Here, he pointed out the missing test output from the AI generated pipeline. We were able to track down to the missing input, in which we prompted the AI to simply add them back. In the process, the AI was messing up the Makefile, causing Oscar to have to spend time fixing it. Later on, I switch to GitHub Copilot with ChatGPT 5.6 Sol as backend for better git integration. We used GitHub Copilot to fix what Gemini has done. Oscar and I were going back and forth to locate the error in the Makefile naming scheme, and put together a solid prompt for Copilot, in which at the end it fixed the error. Once that is out of the way, I ask Copilot to reorganise the output directories, convert them to png for {\LaTeX} import. 

Forth, I move onto writing the report. With the help of Copilot, I was able to import the charts smoothly. I also asked the AI to read my results analysis and cross-check with the output. However, the AI cross-checked with the graph, not the raw numbers. Thus, it got some analysis wrong. It often assumed the Brodal-Okasaki heap would be the worst, but Oscar optimised it so that it would be faster. The AI was prejudiced against this particular heap, given that the naive implementation was actually slow. It was only noticed when we were reading the report again, to which we just go back to the AI and ask it to check again with the number this time. Then, I ask the AI to go through the entire report to polish wording and notations. 

Lastly, I asked the AI to make HTML files for presentation. They contained too much information. So we scraped it and Oscar redesign again with Claude on his time.

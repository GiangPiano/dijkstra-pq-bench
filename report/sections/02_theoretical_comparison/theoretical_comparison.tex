\subsection{Complexity analysis}
\subsubsection{Heap operations}
The theoretical merit of priority queues in shortest-path algorithms can be evaluated by how efficiently they execute three core operations: 
\begin{itemize}
    \item \textsc{Push}: inserting an unvisited frontier node.
    \item \textsc{Pop}: extracting the unvisited node with minimum tentative distance.
    \item \textsc{Decrease-Key}: relaxing an edge to an already-discovered node.
\end{itemize}

\noindent On standard 64-bit systems (\texttt{x86\_64}), pointers and \code{size_t} primitives are 8~bytes in size and require 8-byte alignment boundaries. The physical memory footprint of each node is determined as follows:

\begin{enumerate}
  \item \textbf{Payload (\texttt{Item}):} 
  The fundamental payload stored by all heaps is the \code{Item} struct (\code{int distance}, \code{size_t vertex}). While \code{distance} requires only 4~bytes, the subsequent 8-byte \code{vertex} field forces the compiler to insert 4~bytes of tail padding to maintain 8-byte alignment, bringing $\texttt{sizeof}(\code{Item}) = 16\text{ bytes}$.

  \item \textbf{Binary Heap (16~B node + 8~B handle):} 
  The binary heap allocates no per-node wrapper structs or metadata. Items reside contiguously in a flat array (\code{Item data[]}), consuming exactly 16~bytes per element. When paired with the external index mapping array (\code{size_t pos[]}, 8~bytes per vertex), the total memory allocated per active vertex is exactly:
  \[
    16\text{ B} + 8\text{ B} = 24\text{ B/vertex}
  \]

  \item \textbf{Pairing Heap (40~B node + 8~B handle):} 
  Each \code{Node} contains the 16-byte \code{item} payload followed by three 8-byte pointers: \code{child}, \code{next}, and \code{prev}. Because all members are multiples of 8~bytes, no internal structure padding is required:
  \[
    16\text{ B (item)} + 3 \times 8\text{ B (pointers)} = 40\text{ bytes per node}
  \]
  Accounting for the external \code{Node* pos[]} pointer array yields a combined active footprint of $48\text{ bytes per vertex}$.

  \item \textbf{Fibonacci Heap (56~B node + 8~B handle):} 
  A Fibonacci \code{Node} introduces significant structural metadata:
  \begin{itemize}
    \item \code{Item item}: 16~bytes (offsets $0 \dots 15$)
    \item \code{int degree}: 4~bytes (offsets $16 \dots 19$)
    \item \code{bool marked}: 1~byte (offset $20$)
    \item \emph{Compiler alignment padding}: 3~bytes (offsets $21 \dots 23$) to align the subsequent pointer fields to an 8-byte boundary.
    \item Four pointers (\code{parent}, \code{child}, \code{left}, \code{right}): $4 \times 8 = 32\text{ bytes}$ (offsets $24 \dots 55$)
  \end{itemize}
  This sums to $\texttt{sizeof}(\code{Node}) = 56\text{ bytes}$. With the 8-byte external \code{pos} handle, each settled vertex incurs a memory commitment of $64\text{ bytes}$.

  \item \textbf{Brodal--Okasaki Heap (40~B cell):} 
  The cell buffer stores \code{struct Tree}, consisting of the 16-byte payload, an 8-byte integer \code{rank}, and two 8-byte relative buffer indices (\code{child} and \code{sibling}):
  \[
    16\text{ B (item)} + 8\text{ B (rank)} + 2 \times 8\text{ B (indices)} = 40\text{ bytes per cell}
  \]
\end{enumerate}

\paragraph{Analytical Comparison: Eager vs. Lazy Tradeoffs}
The choice between eager update via \textsc{Decrease-Key} and lazy duplicate insertion fundamentally alters how priority queue overhead is distributed:

\begin{enumerate}
  \item \textbf{The Cost of Position Tracking in Eager Mode:} 
  While eager mode restricts the queue size to at most $n$ items, it imposes a continuous maintenance tax. For array-based binary heaps, every swap during a \code{bubble()} or \code{sink()} must perform a secondary write to update $\texttt{pos}[\code{vertex}]$. In pointer heaps, \textsc{Decrease-Key} requires unlinking and re-melding subtrees. 
  
  \item \textbf{The Elimination of \textsc{Decrease-Key} in Lazy Mode:} 
  Lazy Dijkstra completely bypasses the need for node handles and position synchronization. When an edge $(u, v)$ is relaxed, a fresh \code{(distance, v)} tuple is appended with a simple \textsc{Push}. This transforms edge relaxation from a complex tree-restructuring operation into a trivial insertion.

  \item \textbf{The Penalty of Queue Bloat on Dense Graphs:} 
  The vulnerability of the lazy formulation lies in queue inflation on dense topologies ($m \gg n$). Because stale entries linger in the heap until they float to the root, the queue swells from size $n$ to $O(m)$. Consequently:
  \begin{itemize}
    \item Every extraction incurs tree depth penalties proportional to $\log m$ instead of $\log n$.
    \item The algorithm performs $m$ total extractions rather than $n$. While skipping a stale entry requires only an $O(1)$ scalar distance comparison (\code{d > dist[u]}), getting that stale entry to the top of the heap requires a full, expensive $O(\log m)$ \textsc{Pop} restructuring.
    \item For Fibonacci and pairing heaps, lazy insertion nullifies their asymptotic advantage: their $O(1)$-like decrease-key is never exercised, reducing their theoretical bound from $O(m + n \log n)$ back to $O(m \log m)$.
  \end{itemize}
\end{enumerate}

\noindent
\textbf{Analytical Takeaway:} On sparse graphs ($m \approx 2n \dots 4n$), the number of stale entries is small, so avoiding \code{pos[]} synchronization and pointer cuts allows Lazy Dijkstra to match or exceed Eager Dijkstra in speed. However, as density $m/n$ increases, the cost of $m$ full extractions rapidly overwhelms the cost of $m$ in-place key reductions.

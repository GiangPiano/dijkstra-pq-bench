\section{Theoretical Comparison and Predictions}
\subsection{Complexity analysis}
\subsubsection{Heap operations}
The theoretical merit of priority queues in shortest-path algorithms can be evaluated by how efficiently they execute three core operations: 
\begin{itemize}
    \item \textsc{Push}: inserting an unvisited frontier node.
    \item \textsc{Pop}: extracting the unvisited node with minimum tentative distance.
    \item \textsc{Decrease-Key}: relaxing an edge to an already-discovered node.
\end{itemize}

\noindent On standard 64-bit systems (\texttt{x86\_64}), pointers and \code{size_t} primitives are 8~bytes in size and require 8-byte alignment boundaries. The physical memory footprint of each node is determined as follows:

\begin{enumerate}
  \item \textbf{Payload (\texttt{Item}):} 
  The fundamental payload stored by all heaps is the \code{Item} struct (\code{int distance}, \code{size_t vertex}). While \code{distance} requires only 4~bytes, the subsequent 8-byte \code{vertex} field forces the compiler to insert 4~bytes of tail padding to maintain 8-byte alignment, bringing $\texttt{sizeof}(\code{Item}) = 16\text{ bytes}$.

  \item \textbf{Binary Heap:} 
  The binary heap allocates no per-node wrapper structs or metadata. Items reside contiguously in a flat array (\code{Item data[]}), consuming exactly 16~bytes per element. When paired with the external index mapping array (\code{size_t pos[]}, 8~bytes per vertex), the total memory allocated per active vertex is exactly:
  \[
    16\text{ B} + 8\text{ B} = 24\text{ B/vertex}
  \]

  \item \textbf{Pairing Heap:} 
  Each \code{Node} contains the 16-byte \code{item} payload followed by three 8-byte pointers: \code{child}, \code{next}, and \code{prev}. Because all members are multiples of 8~bytes, no internal structure padding is required:
  \[
    16\text{ B (item)} + 3 \times 8\text{ B (pointers)} = 40\text{ bytes per node}
  \]
  Accounting for the external \code{Node* pos[]} pointer array yields a combined active footprint of $48\text{ bytes per vertex}$.

  \item \textbf{Fibonacci Heap:} 
  A Fibonacci \code{Node} introduces significant structural metadata:
  \begin{itemize}
    \item \code{Item item}: 16~bytes (offsets $0 \dots 15$)
    \item \code{int degree}: 4~bytes (offsets $16 \dots 19$)
    \item \code{bool marked}: 1~byte (offset $20$)
    \item \emph{Compiler alignment padding}: 3~bytes (offsets $21 \dots 23$) to align the subsequent pointer fields to an 8-byte boundary.
    \item Four pointers (\code{parent}, \code{child}, \code{left}, \code{right}): $4 \times 8 = 32\text{ bytes}$ (offsets $24 \dots 55$)
  \end{itemize}
  This sums to $\texttt{sizeof}(\code{Node}) = 56\text{ bytes}$. With the 8-byte external \code{pos} handle, each settled vertex incurs a memory commitment of $64\text{ bytes}$.

  \item \textbf{Brodal--Okasaki Heap:} 
  The cell buffer stores \code{struct Tree}, consisting of the 16-byte payload, an 8-byte integer \code{rank}, and two 8-byte relative buffer indices (\code{child} and \code{sibling}):
  \[
    16\text{ B (item)} + 8\text{ B (rank)} + 2 \times 8\text{ B (indices)} = 40\text{ bytes per cell}
  \]
\end{enumerate}

    \textbf{Fibonacci Heap Complexity} & $O(m + n \log n)$ & $O(m \log m) = O(m \log n)$ \\

    \bottomrule
  \end{tabular}
\end{table}

The choice \textsc{Decrease-Key} and \textsc{lazy} insertion fundamentally alters how priority queue overhead is distributed:

\begin{enumerate}
  \item \textbf{The Position Tracking with \textsc{Decrease-key}:} 
  While eager mode restricts the queue size to at most $n$ items, it imposes a continuous maintenance tax. For array-based binary heaps, every swap during a \code{bubble()} or \code{sink()} must perform a secondary write to update $\texttt{pos}[\code{vertex}]$. In pointer heaps, \textsc{Decrease-Key} requires unlinking and re-melding subtrees. 
  
  \item \textbf{The Elimination of \textsc{Decrease-Key} in \textsc{Lazy} Mode:} 
  \textsc{Lazy} completely bypasses the need for node handles and position synchronisation. When an edge $(u, v)$ is relaxed, a fresh \code{(distance, v)} tuple is appended with a simple \textsc{Push}. This transforms edge relaxation from a complex tree-restructuring operation into a trivial insertion.

  \item \textbf{The Penalty of Queue Bloat on Dense Graphs:} 
  The vulnerability of the lazy formulation lies in queue inflation on dense topologies ($m \gg n$). Because stale entries linger in the heap until they float to the root, the queue swells from size $n$ to $O(m)$. Consequently:
  \begin{itemize}
    \item Every extraction incurs tree depth penalties proportional to $\log m$ instead of $\log n$.
    \item The algorithm performs $m$ total extractions rather than $n$. While skipping a stale entry requires only an $O(1)$ scalar distance comparison (\code{d > dist[u]}), getting that stale entry to the top of the heap requires a full, expensive $O(\log m)$ \textsc{Pop} restructuring.
    \item For Fibonacci and pairing heaps, lazy insertion nullifies their asymptotic advantage: their $O(1)$-like decrease-key is never exercised, reducing their theoretical bound from $O(m + n \log n)$ back to $O(m \log m)$.
  \end{itemize}
\end{enumerate}

\subsection{Experiment hypotheses}
\subsubsection{Hypotheses for Experiment 1: Running time}
\begin{itemize}
  \item \textbf{Hypothesis 1.1:} \\
  On sparse graphs with low average degree ($\bar{d} = m/n \le 4$), edge relaxations are infrequent, meaning Dijkstra's execution is dominated by $n$ vertex extractions (\textsc{Pop}). Because binary heap elements are densely packed in contiguous arrays with zero pointer indirection, the binary heap will achieve the lowest wall-clock runtime, outperforming both pairing and Fibonacci heaps despite having an inferior theoretical decrease-key bound.
  \item \textbf{Hypothesis 1.2:} \\
  As graph density increases ($\bar{d} \gg 32$, $m \gg n$), the number of \textsc{Decrease-Key} operations ($m - n$) will overwhelm the $n$ extractions. 
  \begin{itemize}
    \item We predict that the pairing heap will cross over and beat the binary heap on dense topologies due to its lightweight $O(1)$-like cut-and-meld decrease-key.
    \item Conversely, we predict the Fibonacci heap will fail to beat the pairing heap across all graph densities. This is due to the structural tax of maintaining circular doubly-linked lists, degree arrays, and cascading cut bookkeeping.
  \end{itemize}
  \item \textbf{Hypothesis 1.3:} \\
  The relative performance of \textsc{Lazy} against \textsc{decrease-key} will depend strictly on edge density:
  \begin{itemize}
    \item On \emph{sparse graphs}, \textsc{Lazy} will be faster than or strictly competitive with \textsc{decrease-key} for binary heaps, because avoiding the synchronisation writes to $\texttt{pos}[]$ during \code{bubble()} outweighs the cost of processing a small number of duplicate entries.
    \item On \emph{dense graphs}, \textsc{Lazy} will suffer severe performance degradation across all heaps. The queue will swell to size $O(m)$, forcing the algorithm to execute $m$ full $O(\log m)$ extractions instead of $n$, quickly falling behind \textsc{decrease-key}.
  \end{itemize}
  \item \textbf{Hypothesis 1.4:} \\
  While purely functional priority queues offer optimal theoretical worst-case bounds, simulating \textsc{Decrease-Key} via positive/negative tree cancellation will introduce quadratic-like slowdowns on dense graphs with repeated key updates, rendering it uncompetitive with imperative heaps.
\end{itemize}

\subsubsection{Hypotheses for Experiment 2: Cache Behaviour}
\begin{itemize}
  \item \textbf{Hypothesis 2.1:} \\
  We predict a pronounced gradient in cache miss rates that correlates directly with node size and layout:
  \begin{itemize}
    \item The \textbf{Binary Heap} will exhibit the lowest cache miss rates because traversing an array index ($2i+1, 2i+2$) exploits CPU spatial locality.
    \item \textbf{Pairing and Brodal--Okasaki} will exhibit significantly higher $L_1$ and Last-Level Cache (LLC) miss rates due to pointer chasing. Since individual nodes are allocated arbitrarily in virtual memory, traversing child and sibling pointers will incur frequent pipeline stalls waiting for DRAM round-trips.
    \item The \textbf{Fibonacci Heaps} will record the worst cache behavior because its 56-byte node size approaches an entire 64-byte cache line, minimising the probability that a pointer dereference hits already-cached data.
  \end{itemize}
  \item \textbf{Hypothesis 2.2:} \\
  Array-based heaps will demonstrate lower Instructions per Cycle (IPC) during bubble/sink loops due to data dependency stalls, but will execute orders of magnitude fewer total retired instructions than pointer-based heaps that must maintain multi-way pointer updates per link.
\end{itemize}

\subsubsection{Hypotheses for Experiment 3: Memory Management}
\begin{itemize}
  \item \textbf{Hypothesis 3.1:} \\
  Peak heap memory usage during eager Dijkstra will strictly mirror the analytical struct calculations:
  \[
    \text{Peak Memory: } \text{Binary } < \text{Brodal--Okasaki } < \text{Pairing } < \text{Fibonacci }
  \]
  In lazy mode, peak heap memory will scale with edge volume ($m$) rather than vertex count ($n$), consuming multiples of the eager memory footprint on dense graphs due to duplicate frontier nodes. Furthermore, pointer heaps will show disproportionately higher Peak Resident Set Size (RSS) due to heap arena fragmentation across scattered 40--56 byte allocations.
  \item \textbf{Hypothesis 3.2:}
  \begin{itemize}
    \item \textbf{Buffer-backed Heaps (Binary \& Brodal--Okasaki):} Will incur $\mathcal{O}(1)$ dynamic memory allocations, relying on pre-allocated contiguous buffers and internal free-list management rather than issuing requests to the system allocator.
    \item \textbf{Pointer Heaps (Pairing \& Fibonacci):} Will generate massive allocator churn ($\sim n$ invocations of \code{malloc()} and \code{free()} in eager mode, and $\sim m$ in lazy mode), introducing memory manager bookkeeping overhead and cache eviction during node construction.
  \end{itemize}
\end{itemize}

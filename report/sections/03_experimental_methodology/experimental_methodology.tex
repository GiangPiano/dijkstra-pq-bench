\section{Experiment Methodology}

\subsection{Overview}

All tests were conducted on a machine equipped with an Intel Core Ultra 7
165U processor, 12 physical cores and 14 logical CPUs, 30~GiB of RAM, and a
937~GB NVMe solid-state drive. The machine was running 64-bit \emph{Arch} Linux with
kernel version 7.2.11-arch1-1. All code was compiled with GCC using
\code{-O3 -std=c11}. The final measurements were taken on mains power with the
operating system's performance power profile; an earlier run on default
settings let the processor throttle partway through one benchmark (Section~5).
The complete test suite was executed on Linux, while macOS supports only the runtime benchmarks because the \code{perf} and memory benchmarks depend on Linux-specific facilities. Due to high
variance out of our control we do not expect every machine to produce the same
results, or even subsequent runs to produce the same results, but they should
all be relatively similar.

We tested each heap implementation against two Dijkstra implementations and
several input graphs, gathering data about the running time, cpu behaviour, and
memory use.
In order to reuse code for each task we used \code{make} to generate several
executables, with each executable testing one aspect of a particular heap
implementation, each executable links common objects (\code{dijkstras.o}, \code{graph.o}), the
input graph objects (\code{graph_registry.o}, \code{uniform_sparse.o}, \code{uniform_medium.o},
...), a specific heap implementation's object(s) (\code{binary.o}, \code{fibonacci.o}, ...),
and an entry point (\code{runtime/main.o}, \code{perf/main.o}, \code{mem/main.o}). Thus producing an
executable that will test the specified performance aspect of a particular heap
for all the input graphs.

We used python to generate input graphs as source C files, enabling the produced
executables to automatically discover the input graphs. This allows most of the
test options to be derived from the Makefile. Random number generation during
this process is done using a fixed seed, ensuring that the input data is always
the same across different machines and builds. Compiling and linking the large
graphs means that fresh build times are higher, but all the benchmarks run
quickly, as there isn't additional overhead of reading and parsing large input
files.

Reproducibility was a focus of the test setup. A guix manifest file allows a
user to get all the dependencies of the project on Linux and run the full
pipeline in an isolated container easily.

We used \code{ubench}, a single header C benchmarking library to run our runtime
benchmarks. \code{ubench} first times a single run to choose a batch of
between 10 and 500 runs (about 100~ms of work), then repeats batches of
increasing size until the 99\% confidence interval of the mean is within 5\%.
This allows us to gather a good estimate of
the running time of each heap implementation in both \code{decrease_key} and \code{lazy}
Dijkstras implementations. We took care to ensure that the benchmarks were only
measuring the running time of Dijkstras over the heap implementation, and that
we were not including static overheads due to test initialisation or additional
allocations into the benchmarks. Before timing, each runtime benchmark runs
Dijkstra once and compares a checksum of the resulting distance array with one
computed by an independent Python implementation when the graph was generated,
so every timed configuration is also verified to be correct. This pass also
warms the caches before the timed runs begin.

The runtime and \code{perf} benchmarks are pinned to a single CPU with
\code{taskset}. On a hybrid processor such as the Core Ultra 7 165U the type of
core decides the caches a run sees (a P-core has a 48~KiB L1 data cache and its
own 2~MiB L2, while the E-cores have smaller L1 caches and share an L2), so
\code{src/bench/bench_cpu.py} selects a performance core automatically. On
machines without \code{taskset}, such as macOS, the benchmarks run unpinned.

On Linux, we use the \code{perf} tool to measure data about the cycles, branching,
and cache loads and misses that occur as Dijkstra runs. \code{perf} starts with
its counters disabled, and the benchmark binary enables them only around the
timed Dijkstra loop, so process start-up, graph construction and a warm-up run
are excluded. Each configuration is measured over 50 runs and the counts are
reported per run. We were interested in measuring
the reasons behind the performance differences, and in modern processors cache
locality has a massive impact on program performance. This is where the
difference between the theoretical big-$\mathcal{O}$ performance of each heap and the
reality will be made apparent. We use a python script to run the binaries and
collate the produced data.

Also on Linux we do a separate test for memory usage, this time wrapping the
stdlib's \code{malloc}, \code{calloc}, \code{realloc}, and \code{free} with custom functions to
capture the allocation behaviours and memory usage of each heap. This data is
related to the cache performance measured in \code{perf}, but measured using totally
different techniques, so we are looking to compare the data from \code{mem} against the
data from \code{perf} to see how allocations relate to cache locality. This benchmark
also uses a python script to run the binaries and collate the produced data.

Each test (\code{runtime}, \code{perf}, \code{mem}) produces csvs of the results, which we then
process into svg graphics and \TeX\ files using more python scripts, allowing
them to be easily embedded into the report.

\subsection{Input Graphs}

To compare the priority queues under different workload shapes, we use seven
deterministically generated directed graphs. The graph definitions are kept in
the Makefile, while \code{src/bench/gen.py} generates the corresponding C
source files. Every graph uses the fixed seed \code{67}, positive integer edge
weights drawn uniformly from 1 to 100 (1 to 50 for \code{smoke_1k}), and the
same generated input for every heap implementation and Dijkstra variant.
Dijkstra always starts from vertex~0.

The suite combines uniform random graphs with structured graphs. The uniform
graphs vary the number of vertices and average out-degree, allowing us to
observe how the priority queues behave as the number of edge relaxations
increases. The structured graphs represent workload patterns that are not
captured well by uniform random sampling, such as bounded-degree spatial
networks, concentrated hubs, and broad layered frontiers.

The \code{smoke_1k} graph is included as a small and inexpensive validation
case. It allows graph construction, executable linking, checksum validation,
and benchmark execution to be checked without the cost of the larger inputs.
The three uniform graphs provide a controlled progression from sparse to dense
connectivity. Their increasing average out-degree produces more edge
relaxations and changes the amount of work performed by the priority queue.

The uniform graphs sample $m$ distinct ordered vertex pairs without
replacement, so they contain no self-loops or parallel edges. The
\code{grid_224} graph is a directed four-neighbour grid. Each interior
vertex has up to four outgoing edges, producing a bounded-degree graph with
spatial structure and longer paths than the uniform random graphs. The
\code{hub_skewed} graph contains a concentrated set of 32 hubs together with
background edges: every other vertex has an edge to and from hub $u \bmod 32$,
and each remaining edge has a random source and, with probability $0.75$, a
hub as its target. This creates highly uneven vertex degrees and bursts of
relaxation activity. Finally, \code{layered_frontier} contains 100 layers of
200 vertices, with deterministic forward edges between consecutive layers: each vertex
has edges to 8 vertices of the next layer chosen by a fixed pattern, so only
the weights are random.
Its broad active frontier is useful for observing heap growth and the
difference between eager decrease-key and lazy duplicate-entry Dijkstra.

All seven graphs are used in every benchmark category. The generated graph
sources are written below \code{build/test/}, and the generated registry and
metadata are written to \code{build/test/graph_registry.c} and
\code{build/test/graphs.json}. The graph objects are linked directly into the
runtime, perf, and memory benchmark executables, so the benchmark runs do not
include graph-file parsing or input-loading overhead.

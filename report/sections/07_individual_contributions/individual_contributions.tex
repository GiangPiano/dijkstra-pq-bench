\section{Individual Contributions and Reflections}
\subsection{Oscar Chevalier}

I worked primarily on the Brodal-Okasaki heap, both initially implementing it
and optimising it. My next major role was to maintain the project more
generally. I did all the work on the build system (Makefiles), ensuring the
build process is flexible, correctly captures dependencies to trigger re-builds,
and easy to maintain. In order to do this I spent time orchestrating the group
towards end goals and providing starting points for others to work on, and then
adjusting their work so that everyone could build and run the project, and that
the layout was easy to understand. This lent me a strong understanding of the
project as a whole, and the overall experimental design. Given this, I wrote the
experimental methodology section of the report, and produced the video
presentation slides.

The Brodal-Okasaki heap is a very complex design. While I understand the major
design aspects of Brodal-Okasaki, I am not sure I fully understand the way in
which those aspects interact and flow together. Specifically, I understand that
the skew-binomial tree allows for $\mathcal{O}(1)$ \code{heap_push} operations,
and much of the complexity comes from maintaining the invariants of
skew-binomial tree links. However, looking at the functions and code that
maintain those invariants makes this understanding go out the window, especially
when it comes to removing the minimum element.

Further optimising it for cache locality made this even harder to understand.
It was particularly difficult to get all the little helper methods correct
during the rewrite, as it was hard to understand the role each one played in the
larger picture, and easy to mix up the sibling and child addresses, causing a
hard to find bug. In contrast, while cache locality was initially a concern,
once I realised I could allocate all the cells in a continuous buffer and use
buffer-relative addressing, the problem seems to have been addressed rather
well, and it was a fun solution to the problem.

The worst cases for Brodal-Okasaki are made very apparent in this experiment,
\code{decrease_key} is a nightmare! Supporting it was a lot of extra work, and
not a part of the original paper due to how unfriendly the operation is to
persistent data structures. I believe there are other approaches to support
\code{decrease_key} in persistent min heaps, but the negative queue idea seemed
appealing to try. The additional invariants that needed to be maintained around
negative queue elements added significant complexity to the design.

If starting the project again, I think I'd pick the regular Brodal queue, which
is also a skew-binomial tree, but more similar to the fibonacci heap, using
parent links and double links to improve performance. It would also be
interesting to apply similar memory management approaches to the fibonacci and
pairing heaps, and see if better memory management techniques could allow one of
the high allocation heaps to beat the binary heap.

Maintaining the project build was a secondary but also interesting task. I
already knew how to use make, but this was a lesson in maintaining a larger and
more complex build with it. Make is probably the only build system that can do
semi-incremental builds and can do such a complex arrangement of inputs and
outputs, using and invoking a large range of system tools, however at this level
of complexity it was clear that make was barely holding up. I needed to rewrite
large parts of the Makefile ~4 times as the structure of the project changed,
and we added more components. Make would do well to be replaced with a more
capable programming language while still supporting the ability to interact well
with a wide range of other programs. When issues occurred due to variable
expansion or similar it was hard to debug the Makefile. Extending this project
would make me seriously consider writing something to replace make. We also
temporarily considered \code{nob.h} or \code{nobuild.h} which only uses c to
build c code, however it did not seem mature enough. Still, it beats gradle any
day of the week.

Overall this was a lot of fun, and the broad scope of the project brought a lot
of interesting challenges to solve with a set of tools I do not usually use,
which is always a good way to expand your skillset.

\subsection{Truong Giang Nguyen}

I implemented the base Dijkstra's algorithm for benchmarking. Since C has no
dynamically sized array, I could not simply represent the graph using a normal
adjacency matrix. Implementing one from scratch could introduce allocation
overhead unrelated to the benchmark, so I implemented the shared graph
representation using Compressed Sparse Row (CSR) format.

My algorithm is the binary heap. It has logarithmic time complexity for push,
pop, and decrease-key, and offers constant-time minimum queries. The worst case
happens when relaxation keeps succeeding and constantly pushes new lower values
onto the heap. For the lazy variant, this causes the heap to store a large
number of stale entries and grow in size, making the bubble-up and sink-down
operations longer. If every newly encountered edge adds a new entry to the heap,
the result is $\mathcal{O}(\log m)$ push and pop operations, where $m$ is the
number of edges. Stale entries also cause more pops, which wastes computation
just to reach a valid entry. The second variant, eager, mitigates this by
calling \code{heap_decrease_key()}, which directly alters the entry instead of
pushing a new one. This approach, however, requires an extra index array to
store each entry's position in the heap. The number of successful relaxations is
positively correlated with graph density, as more edges come in and out of each
vertex. Although the worst case can be crafted manually by deliberately placing
edge weights in a certain order, it is extremely rare with randomised input. As
a result, the binary heap won all test cases because of its contiguous data
allocation, which gives it a large advantage in cache locality.

The hardest bug I encountered was in \code{heap_pop}. The assertion I wrote
fired in \code{heap_decrease_key} instead, so I spent a lot of time around the
wrong function. I decided to use Claude Code to review my code, and it turned
out I copied the last element to the root before decrementing \code{size}, so
\code{h->data[0] = h->data[h->size]} read the slot one past the end. This only
corrupts the heap when that stale slot happens to hold a value smaller than the
true minimum, so small graphs passed while large ones returned wrong distances.
The fix was simply to decrement first, then copy.

A key design decision I made was the \code{pos[]} array mapping for the
vertices. Without it, decrease-key would need a $\Theta(n)$ scan to find the
corresponding key. I had to refactor almost every function in the binary heap
implementation, as all operations need to update and keep track of the position
of each added or removed node. It also introduces an extra memory allocation for
the array, which affects the lazy variant even though it never reads it.

If I were to do it differently, I would split the heap into two versions:
\code{lazy_binary_heap}, which does not support \code{decrease_key}, and
\code{eager_binary_heap}. This would give me the rawest benchmark of the lazy
variant of Dijkstra's algorithm. I would then compare it to C++'s
\code{std::priority_queue}, as it is also implemented as a binary heap and does
not support \code{decrease_key}.

\subsection{Tung Nguyen}
\subsubsection{Pairing Heap}

The worst case for the pairing heap occurs during \textsc{Delete-Min}. In this implementation, removing the root first pairs its children
from left to right and then melds the resulting trees from right to left.
Therefore, an input that creates a large root with many children, such as a
dense graph with many frontier relaxations, can make one extraction expensive.
Repeated decrease-key operations can also create irregular tree shapes because
a decreased node is cut from its current sibling list and melded back with the
root.

The hardest design issue was maintaining the left-child/right-sibling
representation correctly. Each node stores a \code{child}, \code{next}, and
\code{prev} pointer. But, \code{prev} has two meanings as it refers to the parent
when the node is the first child, and to the previous sibling otherwise. This
made cutting a node during \textsc{Decrease-Key} particularly error-prone. A
mistake in either case could disconnect part of the tree or leave an invalid
pointer for the next operation. I resolved this by treating the two cases
separately and updating both the predecessor and successor whenever a node was
removed.

If I implemented the pairing heap again, I would define explicit helper
functions for unlinking a node and for appending a child before writing the
main operations. I would also add invariant checks after every operation,
including checks that the root has no parent, sibling links are symmetric, and
every node appears in the position array exactly once. This would make pointer
errors easier to isolate than debugging them through a complete Dijkstra run.

Before this project, I did not fully understand the purpose of \textsc{Meld} in a pairing heap. I now understand that it is the core operation used to combine trees during insertion, \textsc{Decrease-Key}, and \textsc{Delete-Min}. By linking the larger root under the smaller one, the heap preserves the heap-order property without requiring global rebalancing.
\subsubsection{Fibonacci Heap}

The worst case for the Fibonacci heap is associated with \textsc{Extract-Min}
and cascading cuts. Extracting the minimum can require consolidating many roots
of equal degree, while a sequence of decrease-key operations can repeatedly
cut nodes from their parents and propagate cascading cuts up the tree. Dense
graphs with many successful edge relaxations are therefore a natural stress
case because they produce frequent decrease-key operations followed by
consolidation.

The most difficult part was maintaining the circular doubly-linked root and
child lists. Every insertion, cut, child promotion, and tree link modifies
several links at once. In particular, \textsc{Extract-Min} must promote all
children of the removed node, remove that node from the root list, and then
rebuild the list after consolidation. I also had to preserve the marked-bit
invariant, where the first child loss marks a node, while a later loss cuts it and
continues the cascading cut. I resolved these issues by isolating linking and
cutting into helper functions and by carefully resetting parent and mark fields
when nodes became roots.

If I started again, I would first implement and test the circular-list
operations independently before integrating them with Dijkstra. I would also
avoid relying on a fixed \code{MAX_DEGREE} without documenting the bound and
would use a dynamically sized consolidation array based on the heap size.

The main thing I learned is that Fibonacci heaps achieve their theoretical advantage by postponing work rather than eliminating it. At first, I was tempted to optimise the implementation to make every operation appear efficient. But I eventually realised that the main constraint is the trade-off between cheap insertions and decrease-key operations and the more expensive restructuring performed during \textsc{Extract-Min}. I accepted this trade-off as an essential part of the Fibonacci heap rather than trying to eliminate it.
